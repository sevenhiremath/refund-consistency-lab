Integrate

Send your own refund notifications.

A trusted backend registers a payment and its refunds, delivers already normalized provider notifications, and reads back the resulting refund status.

Access

The integration routes require an API key configured on the server, read from the INTEGRATION_API_KEY environment variable. Send it as a bearer token in the Authorization header.

With no key configured the integration routes are unavailable and answer 404. The public demo keeps working without one. The key is never accepted in a URL and never appears in a response.

The flow

  1. 1

    Create a workspace

    One payment, one provider identity, integer paise in INR.

    POST /v1/workspaces

  2. 2

    Register refund intents

    Partial refunds are admitted against the captured amount before any provider is asked.

    POST /v1/workspaces/{id}/refunds

  3. 3

    Deliver notifications

    One normalized observation per delivery attempt. Repeated deliveries of the same matching event count once.

    POST /v1/workspaces/{id}/deliveries

  4. 4

    Read status and evidence

    Confirmed amounts, amounts under review, and the stored reasons.

    GET /v1/workspaces/{id}

Request shape

POST /v1/workspaces
Authorization: Bearer $INTEGRATION_API_KEY
Content-Type: application/json

{"provider":"psp_x","payment_id":"pay_1","captured_paise":100000}
POST /v1/workspaces/{id}/refunds
{"refund_id":"R1","amount_paise":30000}
POST /v1/workspaces/{id}/deliveries
{"attempt_id":"a1","event_id":"E8","refund_id":"R1",
 "status":"succeeded","amount_paise":30000}

Amounts must be JSON numbers in integer paise. Strings, floats and booleans are rejected. Identifiers are bounded, unknown fields are refused, and the notification origin is fixed to a webhook on the server.

Response shape

A delivery reports the recorded outcome and the refund's resulting status separately, because a recorded delivery does not mean the refund succeeded. 

{"outcome":"accepted","recorded":true,
 "refund":{"refund_id":"R1","status":"succeeded",
           "confirmed_paise":30000,"review_paise":0,"reasons":[]}}

Runnable example

examples/integration_client.py is a second application using the service. It imports nothing from the lab, and its notifications travel through the real API. 

python -m pip install httpx
set LAB_BASE_URL=http://127.0.0.1:8031
set INTEGRATION_API_KEY=your-key
python examples\integration_client.py

The example creates a workspace with a 100000 paise capture, registers a 30000 paise refund, delivers one success three times under three attempt ids, retries an identical attempt, and checks a later pending event does not move a settled refund. It does not retry workspace creation, because that endpoint makes a new workspace each time it succeeds.

Hyperswitch webhook adapter

A separate route accepts a real Hyperswitch refund webhook and hands it to the same processing service. It is not part of /v1 and does not use the bearer key, because the caller is the provider. 

POST /webhooks/hyperswitch
X-Webhook-Signature-512: <hex digest>

The signature is an HMAC-SHA512 of the exact raw request body using the signing secret, compared in constant time before the body is parsed. A wrong digest or a tampered body is rejected with 401 and nothing is written.

Configuration is all server side. The route answers 404 unless every value is set:

  • HYPERSWITCH_WEBHOOK_SECRET signing secret
  • HYPERSWITCH_WORKSPACE_ID the one workspace deliveries land in
  • HYPERSWITCH_MERCHANT_ID expected merchant
  • HYPERSWITCH_PAYMENT_ID expected payment

The merchant and payment are bound by configuration, never by the payload, so a body naming another merchant or payment is refused with 403. The refund intent must already exist and its intended amount is never rewritten.

Supported events are refund_succeeded and refund_failed, and the event type must agree with the refund object's status. Any other event, status or currency is refused with 422 rather than coerced. An INR amount that differs from the intent is passed through, so the existing processor keeps it as review evidence.

Verified over HTTP using a signed documented sample, not a delivery from a live Hyperswitch account. The sample in the repository is built from the official webhook and refund schemas.

What is still not implemented

Real provider lookup. There is no route that asks a provider for a refund's current state, and no provider credentials are held. The lookup you can try in the demo is simulated and stays inside the demonstration, so the API never answers from fixture truth.

Duplicate handling does not need a lookup. Repeated deliveries of the same matching event count once. If two claims about one event disagree, both are kept as evidence and the refund stays under review.
